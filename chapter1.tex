\section{Background}
In this section we will give an overview of the background this thesis project is based upon. We will briefly introduce the big data concept and its analytics derivation. We will focus then on what it is the state of the art concerning software architectures for big data collection and analysis giving pros and cons of every analyzed solution. 
\subsection{Big Data}
Big data is one of the trending terms in the IT field which increased of popularity from 2012 \cite{bib10}. A lot of definitions has been given to it \cite{bib11}, focusing on different aspects regarding the data themselves and the infrastructures needed to process them.\\
Despite the recent dramatic increase of popularity, big data is a concept first coined in early 2000s, L. Douglas introduced in its report, a 3Vs concept concerning the new challenges that systems had to deal with, in terms of data feature: Volume, Velocity, Variety \cite{bib12}. The report focalized on what are the problematic due to the increasing size of data, their frequency at which they are produced and a wider range of representation formats. Since 2001, when this report has been published, the question about big data hasn't changed a lot. Now we have better approaches and technologies, but also the big data concept changed. We entered in the IoT era, where every device has internet access, from smartphones to electronic furnitures. Hence the massive amount of data needs new technologies for processing and analyzing it.  A study from McKinsey Global Institute \cite{bib17} stated that the amount of data will grow by 40\% within 2020, and most likely this trend will not end soon. Big steps in technology has been made to handle this ever-growing data amount: for instance, traditional RDBMS have shown their limit in scalability, hence a NoSQL solution is generally preferred since the data load can be spread across several machines. 
Moreover, we switch from physical servers to cloud computing, where virtual resources can be requested on demand only when needed, avoiding for a company the burden of investing a lot of money in a static architecture solution. \\
For what stated above, there is an endless need of new patterns and solutions for big data processing and the aim of this thesis is to investigate a new approach called \textbf{lambda architecture}  (section  \ref{lambda-architecture} ) applied to a subgenre of big data analysis: big data web analytics.

\section{Introduction to web analytics}
The discipline of web analytics started in the early 1990s, as a consequence of the diffusion of public internet \cite{bib13}. Since then, monitoring users activity has become crucial, specially for business purposes, in order to improve efficiency and quality in organizations and services. \\Almost every online business keeps track of their users, not only their actions (for instance: visiting a certain webpage), but also information about devices used for accessing internet, connection speed, browser version and so on. Normally these information are then analyzed and used for user behaviour prediction and contents improving, like designing the user interface for a certain webpage \cite{bib14}. Clickstream data is the primary source of web analytics, it refers to the data collected from users activity, which are every kind of interactions with the website.\\
Nevertheless, web analytics scope is not enclosed into what stated above, typical use cases involve also social network analysis, security informatics or artificial intelligence \cite{bib15}, \cite{bib16}. Despite the use case, web analytics is just the first step in the overall process of data analysis: data need anyway to be understood by analysts for effective decision making strategies.

\subsection{Web analytics metrics}
Define appropriate indicators for web analytics is challenging. Big data became a powerfull source of information only when a sense is given to them, hence standard terms and metrics are needed for the process of analyzing them. Digital Analytics Association (formerly Web Analytics Association) was founded in 2004 with the mission to make analytics a professional discipline for the business, providing a set of common terms, definitions and best practices. A DAA document \cite{bib27} from 2008 classifies web metrics in two categories:
\begin{itemize}
\item \textit{count}: the most basic unit of measure. An example is the number of visitors for a web page
\item \textit{ratio}: a derived metric, obtained dividing a metric by another one. An example is the number of page views per session
\end{itemize}
A web metric can be \textit{aggregate}, \textit{segmented} or \textit{individual}. An aggregate metric is applied to the totality of traffic for a website, a segmented one only to a subset of traffic, and an individual one refers to the one generated by a single user. Examples of it is the average session time for the totality of the users, for the ones connected from a particular nation and for a single user.\\
Even though DAA tried to standardize web analytics, there is still a certain degree of subjectivity when defining web metrics. A clear example is the concept of user session: for DAA a session ends after a logout event or a timeout of 30 minutes. Google Analytics \footnote{https://support.google.com/analytics/answer/2731565?hl=it} instead, defines a session as a sequence of user actions valid till one of the following event occurs:
\begin{itemize}
\item the user stays idle for 30 min.
\item day-change at midnight
\item the user change the adv. campaign for accessing the website.
\end{itemize}

\subsection{A concrete example: Google Analytics}
Google launched its analytics service in 2005 and released a free to use version one year later. Soon it became one of the most used tools for website data analytics.\\
GA tracks the user behaviour through a combination of a javascript library called \textit{analytics.js} and cookies set on user browser for its identification. What made this tool so famous is probably its usability: no particular IT knowledge is required to set the tool up and running:  a website owner can simply set via web console all the metrics needed.

By default GA uses a javascript snippet called \textit{google analytics tracking code (GATC)}, which is injected into webpages. As the browser loads a page as a consequence of an HTTP request, GATC is activated and it requests the \textit{analytics.js} library from Google servers needed for performing the actual data collection via tracker objects. HTTP requests contain valuable information about the client executing the request itself, such as user agent, hostname, origin and language. In addition \textit{analytics.js} sets and reads \textit{first-party} cookies to keep track of the current user. After the tracking has been complete, data are sent to the GA servers as a list of attached parameters to a single-pixel GIF image request for being processed and analyzed.\\
There are several issues related to GA which can mine its accuracy. The first is about the cookie usage: setting a cookie identifies a particular user when data are sent to the server for being analyzed. If the user deletes the cookies set by the analytics library, it will be considered as a new user by the server, altering then the analysis (for instance when tracking the number of unique visitors on a web page). Secondly, GA uses sampling, which means that not all the clickstream is gathered and analyzed, but only a sample of it. This can clearly lead to a drop in final results accuracy.

\section{State of the art for data system}
As stated above, dealing with analytics data could be misleading, and sometimes \textit{key performance indicators} could be interpreted in different ways. Because of this, a lot of companies prefer to build their own in-house analytics system rather than use a commercial one (like GA). Analytics systems are a particular case of Big Data systems, then when designing and developing them, we can apply the same theoretical background. Distributed systems are normally preferred in place of standalone architectures as they offer better performances due to scalability, but they has also some drawbacks: they are complex and less consistent due to the distributed nature.
Currently big data systems fall into these two categories:
\begin{itemize}
\item \textit{batch processing} of big volume of data with high latency.
\item \textit{real-time processing} with short latency (milliseconds) of a stream of data.
\end{itemize}
Batch solutions have been very popular in the last years, specially after Google's publication about \textit{Map-Reduce} computation paradigm \cite{bib25}. Its general approach consist into a set intermediate of key-value pairs is generated after a \textit{map} function, and a final set of key-value pairs is the result of a \textit{reduce} function applied to intermediate sets which are aggregated by the same keys. The aim is to merge input values in order to generate a possibly smaller set of values. Map-Reduce provides for a high level of abstraction over parallel and distributed computation: a programmer only needs to define a map and a reduce function and as a result the computation is spread across several nodes in a cluster. A classic example of this is counting the occurrences of each word in a document. A map function for this problem takes in input a line of the document and emits a tuple for each word in the line. The corresponding reduce function instead just counts the number of tuple received for a key (tuples are distributed across the reducer task by key). There exist several opensource solutions inspired to Map-Reduce, the most famous one is Hadoop\footnote{http://hadoop.apache.org}.\\
Real-time computation has been introduced to overcome to the high latency which characterizes the execution of a batch process. Data are considered as a stream and the goal is to process them as fast as possible. This approach is often coupled with business intelligence and data mining processes. An interesting overview \cite{bib26} defines real-time processing system as a natural evolution of traditional DBMSs. Even if there are substantial differences, as for instance that data needs to be stored before being processed, both systems process incoming data with a sequence of transformation based on common SQL operation defined by relational algebra like \textit{joins}, \textit{filters} or \textit{selections}.\\
A third minor class of data processing handles big data \textit{in-memory}.  A study from 2012 \cite{bib18} predict the in-memory processing will soon overcome the classical batch approach. It highlights the benefits of having a fast data processing system, specially when it comes to react fast to new data with decision making processes. Of course one of the drawback of this approach is the cost: memory is 10 times more expensive that disks, hence companies should go for such a system only when really needed. Another possible issue is related to the dimension of the data to be analyzed: a dataset could be to big to be kept in memory. In these situations, a batch approach is generally preferred.

\subsection{CAP theorem limitation}
CAP (Consistency-Availability-Partition) theorem states that, in every system, only two of the three previous features can be achieved. In presence of distributed systems we are forced to have network partitions, then the CAP theorem says that we could only choose consistency over availability or vice versa. This means that we can either have a system capable of always serving user requests sacrificing the consistency, or a system that sometime isn't available, but gives out consistent data (with all the partitions). Keeping this in mind, we will explore the state of the art for the class of system architectures which aims to mitigate the effects of this theorem.
\subsection{Lambda Architecture}
\label{lambda-architecture}
Data system are particularly influenced by CAP theorem, so a different approach is needed in order to find a tradeoff between availability and consistency. As stated before, a system can perform batch or (nearly) real-time operations on its data. We will explain in the next sections how Lambda architecture aims to find a balance between them.
\subsubsection{Motivations and architecture}
Lambda architecture is an architectural pattern for big data processing system proposed by Nathan Marz \cite{bib2}. It aims to address to the problem of querying a data system giving result \textit{as much as possible synchronized} with the input data. This imply a user to be able to query the system in real-time in order to obtain information on the current state but also on historical data. \\
According to its manifesto \cite{bib2}, this type of architecture has to fulfil the following requirements:
\begin{itemize}
\item robustness and fault tolerance against hardware failures and human mistakes
\item low latency of read and update operations
\item scalability
\item generalization in term of different use cases covered by such a system
\item extensibility i.e. the possibility of adding new features easily
\item ad-hoc queries support
\end{itemize}
The purpose of each data system can be summarized into the simple equation $query=function(all \: data)$ \cite{bib2} with the complication that dealing with big data (gigabyte/petabytes), implies query to require a considerable amount of time to be executed: in this case its result could not be consistent with the entire dataset, since while computing it, new data might have been injected into the system. Unfortunately there is no such a single system capable to answer to every kind of query \textit{in real-time}.\\
The first concept introduced by Lambda architecture is to pre-compute query functions \cite{bib4} in order to process them fast: if a user, queried a particular timeframe of data, the system would answer immediately by showing the precomputed result. Computing aggregated results imposes high latency, a typical instance of aggregation deals with data collected in the last hours or even days and it may take hours to complete, hence the last step is to fill the gap between aggregated results and new data not covered by aggregations yet.\\
In order to solve this problem, Lambda architecture proposes a three layers pattern composed by:
\begin{itemize}
\item Batch layer
\item Real-time layer
\item Serving layer
\end{itemize}

\begin{figure}[h]
        \centering
        \includegraphics[width=12cm]{imgs/lambda-architecture1}
\caption[Lambda-architecture design]{Lambda architecture as union of three layers\cite{bib4} }
        \label{lambda-1}
\end{figure}

Every single datum ingested into the system is replicated into and elaborated by either the batch and real-time layer in order to compute intermediate results (we will refer to them as \textit{batch} and \textit{real-time views}. The outcomes are then merged into the serving layer and ready to be queried by end users. Each layer has different characteristics according to the role they fulfil in the overall architecture.\\
The batch layer is composed by two parts: a master dataset and a batch computation part. The master dataset holds the data coming into the system needed for calculating the aggregated results. Data are considered immutable, no updates or deletion are in theory allowed: data can be appended into or read from the master dataset. We will show later how this is a great advantage in terms of consistency. The batch computation part reads from the master dataset and computes batch views. According to Marz \cite{bib4}, the bath layer would solve the equation $batch \: view=function(all \: data)$. For the latter operation two approaches are possible: incremental and recomputation. The first one implies an update of previous views in order to compute the current one, the second instead involves a total recomputation based only on the raw data stored in the master dataset.  Recomputation algorithms are easier as they result in a simpler logic, while sometimes using incremental algorithms may speed up the whole process as it exploits the existence of already computed results. The choice of the best approach really depends to the use cases the system has to address to. For instance, let's assume we want to calculate the total number of visitors for a webpage over the time. It is easy to understand that for this use case an incremental approach is preferred over a total recomputation on the entire dataset executed everytime new data come.\\
The real-time layer aims to fill the gap introduced by the high latency of the batch layer and it is responsible for providing results on the most recent data. It takes the same input of the batch layer, but instead of storing it in a dataset, elaborates it on-the-fly. It behaves as the batch layer, in terms of pre-computing the same type of views, the difference is that it works only with a small portion of data, exactly the one which it is not covered by batch views. An incremental approach is generally preferred and real-time views are update as new data comes into the system. Formally it solves the equation $real\-time \: view = function(real\-time \: view, new \: data)$ \cite{bib4}. Overall the design of the real-time layer is more complex of the batch layer, either for its incremental approach, either for the requirements it has to respect such as short latency. Fortunately it is only responsible for a small dataset and its views are eventually corrected by the batch ones, so normally a certain degree of approximation is tolerated. We will go more in detail into this in the next section.
\\
The serving layer is responsible for providing results to ad-hoc queries with low latency as a combination of batch and real-time views. It indexes results from the batch layer in order to serve them with low latency and it compensate the lack of batch views for the new data by querying the real-time ones. Hence it gives a final answer to the problem of querying a data system by solving the equation $query = function(batch \: view, real\-time \: view)$ \cite{bib4}. It is the layer with the most complex logic as it has to merge different views according to type of query submitted to the system. A simple case is when the data are time ordered and a particular query refer to a fixed timeframe: the serving layer has just to aggregate batch views with real-time ones (if needed). Though this is just a possible use case and a general purpose implementation of the serving layer might be not trivial.\\

\subsubsection{CAP theorem \& LA}
Even though the audacious title of Marz article about lambda architecture (\textit{i.d. "How to beat CAP theorem"} \cite{bib2}, CAP theorem does still hold \cite{bib5}. What lambda architecture aims to achieve is the so-called eventual consistency. This means, that, after a certain timeframe, data are eventually consistent across all the partitions of a distributed system. \\
We stated before that every single layer of the Lamdba architecture has to respect different constraints due to their different role in the overall system. The master dataset has only to support create and read operations, making then its data an immutable source. This is a great advantage, in the sense that the system does not have to deal with updates, which are one of the causes of lack of consistency in distributed systems. The overall batch layer is eventually consistent in the sense new data are consistent with the query results for a time interval only after the corresponding batch views have been calculated. Moreover, a database supporting random reads and batch writes is normally used for storing such these views.\\
The real-time layer instead, has to be higly available in order to compensate the latency introduced by the batch layer. In order to compute real-time views quickly, approximation algorithms are often used, rather than exact ones (for instance the evalutation of distinct records of a dataset is generally estimated using  \textit{hyperloglog} algorithm \cite{bib6}) and the database used to store the real-time views has to support either random writes and reads due to the incremental approach used by this computation.\\
The overall Lambda architecture based system, as we said, is eventually consistent. Approximations and mistakes made by the real-time layer are eventually corrected by the batch views, once they are computed. 
\subsubsection{Pros and Cons}
One of the main problems lambda architecture wanted to solve is the ability of querying data in real-time. In a certain way this has been achieved: high latency introduced by batch computation is compensated by real-time views and the system is always able to respond to a query, with a certain degree of accuracy as previously stated. This is indeed a great result, specially compared to what we can achieve with regular data system (real-time computation \textbf{or} batch computation).\\
Having an immutable source of data gives to the system robustness against failover : if an error happens on the batch layer (an error in the processing logic or a hardware failure), the entire computation can be re-started without any data loss. Calculation of the final result as a series of transformations of an immutable dataset is a concept also used in batch/micro batch computation framework like Spark \cite{bib8}.\\
The main weakness of such a system is without doubts its complexity. The serving layer is the one with the most complex logic as we explained before, specially in case of non trivial queries. Also, under a developing point of view, implementing and maintaining two different systems is hard. Unfortunately at the moment it does not exist a unified framework in order to share the same logic between the real-time and batch layers. An attempt of unification has been made with twitter summingbird project \cite{bib7}: it provides a high level abstraction for defining the logic of a job and then share it among different framework for batch and real-time computation. Nevertheless this is still a raw project rather than a production-ready solution. Another solution would be to use a module of the Spark ecosystem called Spark Streaming, even though it just simulates a real-time approach by actually performing \textit{micro-batching}.
Another drawback is the lack of flexibility regarding the queries the system can serve. One of the requisite of lambda architecture is the ability to handle \textit{ad-hoc} queries, in the sense they depend on parameters known only at query-time. What lambda architecture lacks instead, is the ability to serve arbitrary queries since it deals only with precomputed views.

Lambda architecture isn't perfect, other solutions and in prof of concept ideas found in literature try to exploit its weaknesses. .....

\subsubsection{Kappa Architecture}
The main competitor of Lambda architecture is an architectural pattern called \textit{Kappa architecture}\cite{bib9} first mentioned by Jay Kreps (project leader of Kafka at Linkedin). This approach claims to beat Lambda architecture in its main weakness: the complexity of the overall system. Kreps says that maintain such a complex system likely lead to lack of synchronization between the real-time and the batch layer as well as a high effort for running and debugging it.\\
The approach proposed with Kappa architecture is to exploit just the real-time computation layer, exploiting a system which able to persist messages over the time (Apache Kafka for instance). In Lambda architecture, real-time and batch layer share the same logic even though they work on replicated dataset. In this approach data are stored and reprocessed several time by the same stream processing logic according to the different time views required by the system. Each processed result is then stored in a serving layer in charge to switch between several views according to the queries executed by end users. In this scenario multiple processing processes working can work in parallel on the same dataset reading it from different points: one coud be processing data from one month ago, one from one week ago and another one could just follow the real-time flow of new data. \\
